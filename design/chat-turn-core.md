# The chat turn core

How `AIChatAgent` (`packages/ai-chat`) and `Think` (`packages/think`) run a chat turn on one shared core in `packages/agents/src/chat`. This is the record of what the core owns today, every place the two classes differed and what was chosen, what still differs, and what is known to be wrong.

[chat-shared-layer.md](./chat-shared-layer.md) describes each file of `agents/chat`. [rfc-chat-turn-core.md](./rfc-chat-turn-core.md) is the decision this work started from.

## How it works

The hosts keep what is theirs. `AIChatAgent` keeps `onChatMessage`, the flat transcript and destructive regenerate. `Think` keeps its inference loop, the Session tree, submissions, actions and channels. The core owns the order things happen in.

The core was built in the phases the RFC proposed. Phases 1, 2 and 4 are implemented, with three pieces that turned up on the way: the before-turn repair, the request context and durable admission of client requests. Phases 3 and 5 are not.

### Turn coordination (Phase 1)

`ChatTurns` (`packages/agents/src/chat/chat-turns.ts`) owns the state a host needs to run one turn at a time, and the rules across it:

| State                                                    | Rule the core now owns                                                                                                     |
| -------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `queue` (`TurnQueue`)                                    | `turnResetGuard()`: a turn runs under the generation it was admitted with. After a clear it must not stream or persist.    |
| `aborts` (`AbortRegistry`) and running recovery attempts | `cancel(id)` reaches a queued turn, a running turn, and a recovery attempt registered with `beginRecoveryAttempt(rootId)`. |
| `submits` (`SubmitConcurrencyController`), `preStream`   | `decideSubmit()`, `awaitSubmitTurn()` (superseded and debounce checks at the front of the queue), `settlePreStreamTurn()`. |
| the tool-result apply chain                              | `applyInteraction()`: applies commit one at a time, and only one that settled its call schedules a continuation.           |
| `continuation`, `autoContinuation`                       | `takeContinuation()`: a continuation runs only while the message it answers is still the latest.                           |
| all of the above                                         | `reset()` tears it down in one synchronous step. `waitForIdle()` and `waitUntilStable()` define idle and stable once.      |

Both hosts construct one `ChatTurns` with a small `ChatTurnsHost` (the transcript, two stream flags, `keepAliveWhile`, an id generator, and `fireContinuation`). Their old private fields (`_turnQueue`, `_continuation`, and so on) are aliases of the core's parts, so tests and subclasses that reach for them still work.

`AIChatAgent` is about 220 lines shorter and `Think` about 110, counting the recovery stop `Think` gained. No public API changes.

### One admission path (Phase 2)

Every way a turn starts goes through one function in the core. The host supplies what each step does. The core owns the order.

| A turn started by                                                                                                   | Core function                     | File                   |
| ------------------------------------------------------------------------------------------------------------------- | --------------------------------- | ---------------------- |
| A client request                                                                                                    | `ChatTurns.runClientRequest()`    | `chat-turns.ts`        |
| The server: `saveMessages`, `continueLastTurn`, the retry turn, a recovered turn, an agent-tool run, `Think.chat()` | `ChatTurns.runServerTurn()`       | `server-turn.ts`       |
| A tool result or approval                                                                                           | `ChatTurns.runContinuationTurn()` | `continuation-turn.ts` |

**Client requests.** `runClientRequest()` owns the sequence both hosts ran: decide concurrency, accept (clear the terminal record, mark the turn pre-stream, create the abort controller), persist the incoming messages, enqueue, run the queued checks, end a request cancelled meanwhile without calling the model, run the turn, and settle. The host passes a `ClientChatRequest` with the steps that differ: how to persist, how to enqueue through its own tracing wrapper, what to run, and which frames to send.

**Server-started turns.** `runServerTurn()` captures the generation, creates the abort controller and links the caller's signal, enqueues, checks for a reset and a stop around the host's `prepare` and `persist`, ends a turn stopped meanwhile without calling the model, runs it, releases the controller and the listener, and maps the status. The host passes a `ServerChatTurn`. A host that already holds the queue slot passes an `enqueue` that runs at once. A caller can pin the tools and body a turn runs with (`pinnedOr`). What it leaves out is the stored value, read when the turn starts.

Each host has one turn body for every server-started turn (`AIChatAgent._runServerTurnReply`, `Think._runModelTurn`). `Think.chat()`, the sub-agent RPC entry, is a server-started turn whose reply goes to the caller's callback. It reads the generation and creates its controller before it tells the caller the request id.

A caller can pass tools and a body with a turn (`PinnedTurnContext`): an agent-tool run's input, or the context of a turn being recovered. A pinned context goes to the model call and into the turn's recovery snapshot and is never written to the stored request context, so there is nothing to put back afterwards and nothing a clear or a tool result can lose.

**The auto-continuation turn.** `runContinuationTurn()` owns it from the fire to the settle: it creates the abort signal, enqueues through the host's wrapper, claims the continuation when the turn starts, runs the host's turn body, reports a failure before the stream, and settles once however the turn ended. `streamStarted()`, `streamEnded()` and `replyFinalized()` are the points a host reports from its reply pipeline. A continuation with no connection, which `Think` runs when an approval arrives over RPC, is the same runner with nothing to claim. A stop of the running turn drops the continuations that were waiting when it landed (`cancel`, `stopAll`, a linked signal).

**What surrounds a turn** is shared too:

- `ChatTurnFibers` (`turn-fiber.ts`) runs a turn body inside the host's recovery fiber and tracks the live turn.
- `reportTurnFailure` (`turn-failure.ts`) fixes the order of a failure report for a request and a continuation: the host's hook, the terminal record, the error frame.
- `AgentToolRuns` (`agent-tool-runs.ts`), with one SQL store (`agent-tool-run-store.ts`), owns an agent-tool child run: the run table, the run's life, cancel, what the parent reads (`inspect`, `chunks`, `tail`) and progress. A host supplies how the run's turn is queued, what its output is, and how a frame is broadcast.

**Before the model is called**, two rules that were not in the first plan are in the core:

- `ChatTurns.settleBeforeTurn()` (`before-turn.ts`) settles what must not reach the model. A message the conversation moved past keeps no unanswered tool call and no approved call left unrun. A continuation turn keeps, in the message it continues, what a client is known to still answer, and does not run while there is any. No assistant message ends in reasoning. The host supplies how a repaired transcript is stored (`RepairedTranscriptSink`).
- `ChatRequestContext` (`request-context.ts`) owns the stored client tools and body: restore, persist, the request rule, the tool-result rule and clear. A host passes a three-method store.

**Durable admission.** A client request that was accepted survives an isolate reset (`ChatAdmissions`, `admissions.ts`). `runClientRequest` writes a record in `cf_agents_chat_admissions` after the concurrency decision: the request id, the new user messages the request holds, the latest user message a tab showed when it was accepted, its concurrency decision, the host's payload and a `stopped` flag. The record is deleted when the turn's fiber is durably accepted, when recovery's wake picks the turn up, or when the request ends any other way. `cancel` and `stopAll` write the stop on the record, and `reset()` deletes every record. A write that fails ends the request with an error frame.

**A turn answers its own message.** A request's new user messages are held on its record, not stored, until its turn reaches the front of the queue. There the host's `join` step stores them after everything stored meanwhile, once (a message an earlier join stored is not stored again), before the superseded check and before a stop is honored, so a superseded or stopped request's question is kept at its place. A request that will not run stores its question too and ends `skipped`. Only a clear drops a waiting message. The transcript reads `U1, A1, U2, A2`, and a model request never holds a later question than the one its turn answers, the running turn's and its recovery's included. Tabs see a waiting message at once: every message list the hosts send ends with the held messages and names them in `queuedMessageIds` (`ChatTurns.clientView`). A tab that connects is sent that list on its socket, without the reply it is about to resume (`connectView`). `useAgentChat` keeps queued messages out of the AI SDK's list and draws them after it (`queued-messages.ts`). The HTTP transcript holds stored messages only.

After a reset the records left are replayed (`ChatAdmissions.resume`), however long they waited: when the host starts, on every terminal incident write, and at the end of every wake and attempt. A replay does nothing while a recovery is pending. Otherwise it restores every record's concurrency decision together, then runs each record through `runClientRequest` in order with no connection, reading it again just before it is queued. Each replay stores its messages when its turn starts. A new request that arrives while records wait replays them first, ahead of itself. `Think` submissions keep their own ledger and wait on the same trigger.

`saveMessages` and `continueLastTurn` have no record: they store nothing until their turn starts, so a reset loses nothing of theirs, and the caller's promise rejects.

### Recovery entry points (Phase 4)

`ChatRecoveryEngine` owns recovery for both hosts. `runRecoveredTurn` (`recovery-attempt.ts`) is the body of a recovery attempt: return if cancelled, register the attempt, settle the cut-off reply, wait until stable, check for a stop before the timeout branch, park or reschedule or give up on timeout, check the leaf, run the turn with the stop signal, record the outcome, and always end the attempt. A throw is caught. `routeStreamInterruption` (`recovery-route.ts`) routes a live stall or transient error into recovery, and `scheduleRecoveredTurn` builds the callback payload in one place. Each host binds its turn machinery once in the adapter's `turns` and passes per-attempt hooks for what differs: the leaf check, the turn, how a partial is stored, and `Think`'s submission and messenger steps. Classify and the retry-or-continue decision after a restart stay in the hosts.

An attempt runs in its own async scope, so a turn another request runs while the attempt waits opens its own incident. A turn that continues the latest reply takes it over from a scheduled recovery once its stream carries content: the first chunk that is not `start`, `start-step`, `finish-step`, `finish`, `error`, `abort` or `message-metadata` (`takeReply`). A continuation that ends before that (a repair or a hook throws, the model call fails, the stream carries only a provider error) leaves the recovery in place, so a cut-off reply always has either a turn continuing it or a recovery scheduled for it.

### Not in the core yet

**The reply pump (Phase 3).** This is the loop itself: take a stream of chunks, build the assistant message, store each chunk for resume, broadcast it, and when the stream ends persist the message and send the terminal frame. Stop early on abort, a stall, a provider error, or a clear.

`_reply` plus `_streamSSEReply` in `AIChatAgent` and `_streamResult` in `Think` do the same steps with different inputs. The recovery RFC already worked out the order of work, and it still holds:

1. Move `AIChatAgent`'s live loop onto `StreamAccumulator`. It hand-rolls `applyChunkToParts` on a shared `_streamingMessage` today. The orphan path already uses the accumulator.
2. Give both hosts one pump in the core that reads `AsyncIterable<UIMessageChunk>`. `AIChatAgent` adapts its `Response` (SSE or plain text) into that. `Think` passes `toUIMessageStream()`.
3. Host hooks cover what differs: where the message is persisted, the early approval persist, replayed provider chunks, `Think`'s overflow retry, the RPC callback sink.

The pump is where the remaining single-host guards live (the reset guard in `_reply`, held terminal frames, the stream-active gate), so this phase is what makes them shared.

**Lining the core up with the harness (Phase 5).** `ThinkHarness` and the other harnesses share one interface (`HarnessSession` in `agents/experimental/channels/harness`): `submit` returns an operation, `wait` settles it, `abort` and `reset` stop work, and a tool answer is submitted like any other input. `ThinkHarness` adds `continue` and `regenerate`.

After Phases 2 to 4 the core has one admission function, one pump and one recovery path. Its vocabulary can then be renamed to the harness's (a turn request is an operation, a tool result is an input). At that point moving the `Think` class to `ThinkHarness` is a change of engine behind an interface both already speak, and the behaviors to preserve are written down once.

This phase is not designed in detail.

## Key decisions: differences between the hosts, and what we chose

The two hosts disagreed in places where nobody decided they should. The rule for choosing was the behavior that is hardest to get wrong at the edges, whichever host had it. Where the two agreed on a behavior that was wrong, the same rule applied.

D1 to D10 came from Phase 1 and the client request. D11 and D12 were found then and settled later. D13 to D18 are recovery, D19 to D24 server-started turns, D25 to D33 the continuation turn, D34 to D47 agent-tool runs and `Think.chat()`, D48 to D54 the before-turn repair and the request context, and D55 to D58 what an end-to-end probe of the stack against `main` found, D59 to D80 what independent reviews, fault injection, an upgrade probe, a browser probe and mutation testing found afterwards, D81 to D86 durable admission of queued requests, D87 to D93 a second review pass, D94 to D100 a third, D101 to D108 the order a queued message is stored in, and D109 to D112 the last review and fuzz of the queue.

Notes:

- **D5.** `Think` fires the hook inside the turn. Both classes document that the turn lock is released first, so `saveMessages` is safe inside the hook. `Think` rejects that call with its "cannot be called from inside an active turn" error. The chosen behavior fixes that and keeps the replay after a restart. It is done for one path: `onChatResponse` for a continuation that failed before its stream runs after the turn left the queue in both classes.
- **D6.** Neither old check was right. Counting every unanswered call waited forever on a server tool whose `execute()` died with its stream. Counting only tools the client sent a schema for ignored a client tool an app declares on the server and answers from `onToolCall`. The fix removes the ambiguity where it starts. A reply whose stream was cut off (a stop, a stall, a provider error, an eviction) is stored with its unanswered calls settled as errors, unless a client is known to own them (`settleInterruptedReply`). An unanswered call in the latest stored message then always belongs to a reply that finished on it, which is what a client tool does, so it counts whatever its tool (`hasPendingToolInteraction`). That holds for replies this version stored. A latest reply an older release stored can hold a dead server call, so a host that can name the tools a client may answer passes them, and only those count there: the client's schemas and the server's tools without `execute`. `Think` passes them. `AIChatAgent` cannot see its tools and counts every call. `ThinkHarness` settles interrupted tool calls the same way. Two narrower cases keep the old rule that only a known client tool counts: the reply that is streaming now, where a server tool is unanswered while it runs, and a reply the conversation has moved past, where an unanswered call cannot be told apart from a dead one an older version stored. Recovery uses the same check. It settles only the cut-off reply it is about to continue, and never changes a reply that finished.
- **D7.** Three things to settle when `AIChatAgent` branches: `maxPersistedMessages` counts stored rows, so hidden branches would count against the limit. Storage grows because old replies are kept. And apps can overwrite the whole transcript (`persistMessages(array)`, assigning `this.messages`), which has no obvious meaning on a tree.
- **D11.** A provider rejects a request that holds a tool call with no result, so a new message sent while a client tool call was pending could never be answered in `AIChatAgent`. Every turn now settles the unanswered calls in messages a later message follows, and a turn that starts a new reply settles the last message too. That includes a call the user approved that never ran: the AI SDK runs an approval only in the last message. A continuation turn continues the last message, so there it keeps a known client's call and an approval request. While it keeps one it has nothing to continue: `continueLastTurn()` returns `skipped` with the reason `awaiting-client`, and the client's answer starts the continuation. The check is made where the continuation is claimed and again where the request is built.
- **D26.** The finish reason is the wrong signal. `Think`'s stream cannot go past a client tool call, so its `stop` does not mean the result was consumed (#2352), and in `AIChatAgent` a result can arrive long after the stream ended. What providers reject is a request that ends in assistant text, and the transcript says whether that is so: `convertToModelMessages` splits an assistant message at `step-start`, and a last step with a tool part ends in that tool's result. A provider-executed tool is skipped, because its result stays in the assistant message. A last step of reasoning alone is not an answer. Every continuation answers at least one message. A `Think` approval of a paused execution targets the message its outcome is stored in, on a connection or not, and `Think` drops the text written after the pause before the check reads the transcript. An approval that arrives after the conversation moved on starts no turn: the outcome is stored, the next turn reads it, and `chat:continuation:dropped` says `moved_on`. One case went the other way: a stream that carries the tool call and the answer in one step, with no `start-step` between them, was dropped on `stop` and now continues.
- **D32.** Both classes continued after a stop, and agreed on it. A result answered while the reply streamed, or one that arrived while a continuation ran, started the model again about 50 ms after the user pressed stop. A stop lands on waiting continuations in four cases: it stops the turn running now; it stops every request (`abortAllRequests`, `cancelAllChats`), running turn or not; it names the reply that just ended, with no turn running; or it comes from a tab that waits on the continuation and has no request id yet (`cf_agent_chat_request_cancel` with `continuation: true`). A result that arrives after the stop continues in every case.
- **D51.** Anthropic rejects an assistant message whose final block is a thinking block. `convertToModelMessages` makes a step that holds only reasoning its own assistant message, and the Anthropic provider joins consecutive assistant messages, so only reasoning with nothing after it in the message is at risk. D26's rule that a reasoning-only last step is not an answer lets the continuation run. This rule is what makes its request valid. A text part with no text is removed with the reasoning: it is the start of an answer the model never wrote.
- **D57.** A reply cut off while the model was still reasoning has no parts left once D51 has run, and a client draws it as an empty bubble. The same holds for a reply cut off before any content. "Nothing" means no part a client can show and none a model request can carry. The rule also removes a reply that finished as reasoning alone, which a model produces when it runs out of output tokens while thinking. The user saw that reply, and the next turn deletes it. It is removed because an `AIChatAgent` app builds its request from the stored messages and Anthropic rejects that shape. `chat:transcript:repaired` carries each removed message as it was stored, so an app can keep a copy. Three things depended on the message being there. A recovery that targets it by id retries the question, and records that and the question on the incident before it removes the reply, so the same payload delivered again still retries that question and no newer one. A continuation is never scheduled for it, because that takes a settled tool call. And in `Think`'s session tree a removed message's children are spliced onto its parent. An agent-tool run whose only reply was empty ends `error` where it ended `completed` with no output.
- **D58.** The merge kept one text block, and it broke when the model reasoned before it went on: the reply read text, then reasoning, and ended in reasoning, which D51 removes a turn later. A tab now gets `text-start` for the continuation's text and shows a second text block, where it used to see the first one grow.

## Still different

What the two classes still do themselves, or differently, after the stack.

`AIChatAgent`:

- **`Retry-After` (D17).** Only a platform-transient reader error is routed into recovery. A provider 429 arrives as an SSE `error` chunk and ends the turn, so the header is never seen.
- **Context overflow (D23).** It has no overflow recovery. The app owns the model call.
- **Regenerate (D7)** deletes the old reply.
- **`onChatResponse` (D5)** is drained after the turn and lost on a restart, except for a failed continuation.
- **The client request's turn body** is a third copy of the turn body, next to `_runServerTurnReply`. It differs by its tracing spans, the "no response" frame and the pre-stream settle.

- **An override of `persistMessages` that writes storage before it calls `super`** is not stopped by a clear. The check is in the base method.
- **Overlapping requests under `messageConcurrency: "merge"`** are stored as one user message. `Think` stores each one and answers once.
- **A clear during a reply** fires `onChatResponse` with `aborted`. `Think` fires nothing.

`Think`:

- **Two reply loops.** `_streamResult` and `_streamResultToRpcCallback` are two copies. `_runModelTurn` picks between them.
- **The connection-less continuation** is triggered by a durable queue item only `Think` has.
- **A declined interruption found after a restart** still sends its "declined" message. There is no stream error to show (D16 covers the live case).

Both, still in the hosts:

- **The reply loop** (Phase 3), with the stream-active gate, the `ResumableStream` wrappers and the resume handshake wiring around it.
- **Classify and the retry-or-continue decision** for a turn found interrupted after a restart. They read a flat array against a session tree.
- **`_exhaustChatRecovery`** sends its frame before the record, the reverse of `reportTurnFailure`. Its reason holds for a give-up.
- **The before-turn step** is called from two places per host: the client request's turn and the shared server-turn body.
- **`continueLastTurn()` over a reply that waits on a client tool whose schema nobody sent** settles that call. Nothing tells it apart from a dead server call.
- **An unanswered approval the conversation moved past** becomes an error that says it did not run, not a denial.

## Known gaps

What is still wrong after the stack, in both classes unless it says otherwise. None of these is new: each was seen on `main` as well, or follows from a rule the stack added and did not finish.

- **A recovered turn that finished just before the isolate died (D63).** The turn ended, its fiber is gone, and the isolate dies before the attempt records the outcome. The second delivery sees the turn's mark and returns, no wake comes, and the incident stays `scheduled` until the expiry sweep. It also holds the replay of waiting requests (D81) until then, or until a new request forces it. Closing it needs a durable "turn ended, with this result" mark.
- **A continuation scheduled or parked when the isolate died** is lost. A later result for a sibling call that does not ask to continue finds nothing pending, and nothing runs.
- **A message waiting at a rollback to `main` (D101)** is on its record only, and `main` never reads the record, so the message is gone from the transcript. An upgrade again replays it: unless the conversation moved on, it is answered, and otherwise it is stored unanswered (D109).
- **Merge in `AIChatAgent` (D103)** stores each waiting question at its turn's place and collapses them when the surviving turn starts, so tabs see the questions stored one by one and then become one message.
- **`Retry-After` in `AIChatAgent` (D17).** A provider 429 arrives as an SSE `error` chunk and ends the turn, so the header is never seen.
- **A tab that resumed a `Think` continuation through the AI SDK (D70)** draws it into the last assistant message until the message list arrives.
- **A reconnecting tab gets one `aborted` frame** before recovery continues the reply (D65).
- **After an isolate reset, the tab that sent the request sometimes misses the continuation.** It ends `ready` with its own partial followed by the stored partial and never shows the recovered text. A reload fixes it.
- **Text a user watched stream can disappear after a reset.** Only the chunks that reached storage before the reset survive, and the recovered reply continues from there.
- **The tab whose request carried a shorter copy of a reply (D59)** keeps drawing it until the next broadcast. Storage and other tabs hold the full reply.
- **The pre-Sessions lift** drops the `content` text of a v4 message that also has `toolInvocations`.
- **A rollback to `main`** with an incident the stack marked `continued_by_interaction` still queued: `main` continues that reply a second time, as it did before D18. Not tested.

The models are checked with everystate, a TLC-compatible TLA+ model checker that needs no Java. The checker runs 191 cases over the ten models. The models are not in the repo yet.

The code is covered by unit tests next to each core file (`packages/agents/src/chat/__tests__/`) and by the host suites. Each behavior change in the table has a test that failed before it. Where a change went into the core, the test is a host test in each class whose behavior moved, and a unit test for the rule.

Mutation testing ran twice. The first run covered the 16 core files (2955 mutants, against the core unit tests and then the host suites). The rules it found unpinned were given tests or, where a guard could not fire, deleted. The second run covered every line changed since, in 25 files: of 1386 mutants the core unit tests kill 1172 (84.6%) and the host suites 42 more (87.6% together). 172 survive, and 25 of those run in no test. Of 171 statement mutants (a deleted step, a swapped pair of awaited steps), 21 survive the core tests.

Independent reviewers, a fault-injection probe, an upgrade probe and a browser probe on deployed Workers compared the stack with `main`: D59 to D100 and [Known gaps](#known-gaps) are what they found.

## Tradeoffs

The core is composed into each host, not inherited, and the two classes were converged on it before either moves onto `ThinkHarness`. What that gave up, from the RFC's alternatives:

**Put `AIChatAgent` and `Think` on `ThinkHarness` now.** This is the destination for `Think`, and the harness design avoids most of these races by construction, because every input is a durable operation in one queue. It is too large a first step. `Think` has features the harness lacks (submissions, actions, channels, extensions, messengers, agent tools), and `AIChatAgent`'s contract (`onChatMessage` returns any `Response`) does not fit a loop that owns the model call. Converging the two classes first makes the later move smaller.

**A shared base class.** `AIChatAgent` and `Think` would extend a common `ChatAgent`. It makes every shared method part of each class's inheritance chain, where subclasses can override it, and it ties the core to `Agent`. `ThinkHarness` is a Lifecycle capability and could never use it. Composition keeps the core usable from a capability.

**Keep porting fixes by hand.** This is what we do now. Three of eight fixes needed a port, and each port was found by looking, not by a failing test.
